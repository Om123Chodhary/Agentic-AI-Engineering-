🚀 Day 20: Productionizing AI Agents (Deployment, Reliability, & Observability)
🎯 Objective
Until Day 19, our AI agents ran locally in a terminal. On Day 20, we transformed our terminal-based Python scripts into a Production-Ready Web Service. We learned how to expose an agent via HTTP, containerize it using Docker, handle failures (Timeouts, Retries, Rate Limiting), implement structured logging, and automate agent evaluation.

🏗️ 1. The API Layer (FastAPI & Pydantic)
We used FastAPI to create a boundary between our internal AI application and the outside world.

The /chat Endpoint: Created a POST endpoint to receive user messages and return agent responses.

Pydantic Validation (schemas.py): Defined strict Request and Response models (ChatRequest, ChatResponse). If a client sends invalid data (e.g., missing the message field), FastAPI automatically returns a 422 Unprocessable Entity error before the request even reaches the LLM, saving compute costs.

Automatic Docs: FastAPI automatically generates Swagger UI at /docs, allowing frontend developers to test the API without writing any code.

🛡️ 2. Production Error Handling
AI dependencies (like Ollama) can crash or hang. We must ensure our API fails gracefully without leaking internal Python stack traces to the user.

HTTP Exceptions: Wrapped the agent execution in a try-except block.

Status Codes:

500 (Internal Server Error): Returned when the LLM fails internally.

504 (Gateway Timeout): Returned when the LLM takes too long to respond.

Security: Log the actual error (logger.exception) internally, but return a clean, generic message to the client (e.g., "Agent execution failed. Please try again later.").

❤️ 3. Health Checks & Application Lifespan
A running process does not mean the service is ready to handle requests.

Liveness (/health): Answers, "Is the FastAPI server alive?" It does not check external dependencies.

Readiness (/ready): Answers, "Is the server ready to serve traffic?" We used httpx to ping Ollama. If Ollama is down, this endpoint returns not_ready.

Lifespan Events (@asynccontextmanager): Used yield to separate startup and shutdown logic. Heavy resources (like MCP clients or Database connections) are initialized before the yield and cleaned up after the yield to prevent memory leaks.

🐳 4. Containerization (Docker & Docker Compose)
Docker packages the application and its runtime dependencies into a reproducible environment.

Dockerfile: Used a python:3.12-slim base image, copied requirements.txt, installed dependencies, and exposed port 8000 using uvicorn main:app --host 0.0.0.0.

The Networking Gotcha: Inside a Docker container, localhost refers to the container itself, not the host machine. To connect to Ollama running on Windows, we used host.docker.internal in the .env file.

Docker Compose (docker-compose.yml): Used to define and run multi-container Docker applications. Added extra_hosts to map the host gateway and configured a healthcheck to ensure Docker monitors the container's health.

⚡ 5. Reliability Patterns (Resilience)
Timeout (asyncio.wait_for): If the LLM takes more than 30 seconds, the request is killed to prevent server resources from hanging.

Retry (tenacity library): If a temporary network glitch occurs, the system retries the operation (up to 2 times) using Exponential Backoff (waiting 1s, then 2s, then 4s) to avoid hammering the failing server.

Rate Limiting (Sliding Window): Prevents DDoS and API cost abuse. We used collections.deque to track timestamps of requests per client IP. If a client exceeds 10 requests per minute, they get a 429 Too Many Requests error.

🕵️ 6. Observability (Structured Logging)
print() statements are useless in production. We used Python's logging module.

Request IDs (UUID): Generated a unique ID (uuid.uuid4()) for every incoming request. This ID is injected into every log message, allowing developers to trace a single request across multiple components.

Metrics: Used time.perf_counter() to calculate the exact duration of the LLM call, helping identify performance bottlenecks.

🧪 7. Automated Agent Evaluation
API success (HTTP 200) does not mean the Agent succeeded. The agent might have called the wrong tool.

Deterministic Checks (run_evaluation.py): We built a test suite with a dataset of questions and expected_tools. The script inspects the result["messages"] to see if the correct tool was invoked. It calculates a Pass/Fail score.

LLM-as-a-Judge: For subjective answers (where there is no single fixed output), a separate LLM is used to evaluate the agent's answer based on Correctness, Relevance, and Clarity (score 1-5).

CI/CD Integration: Evaluation should be part of the deployment pipeline. If the pass score drops below a threshold, deployment should be blocked.

💡 Key Interview Takeaways
API Success ≠ Agent Success: Always evaluate the agent's intermediate steps (tool calls) and not just the final HTTP response code.

Container Networking: localhost inside a container is not your host machine. Use host.docker.internal (Docker Desktop) to communicate with host services.

Fail Gracefully: Never expose raw Python tracebacks to a client. Use structured logging internally and HTTP exceptions externally.

The Three Layers of Protection: Rate Limiting (Traffic control) + Timeout (Hanging prevention) + Retry (Transient failure handling).
